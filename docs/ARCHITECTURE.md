# Architecture: code structure

The rules for how Go code is laid out and how a request flows through it. Generic scaffolding: product behaviour is in the `*_design.md` files and package godoc. Tooling and workflow are in [CONTRIBUTING.md](CONTRIBUTING.md); how this structure is tested is in [TESTING.md](TESTING.md); SQL conventions are in [DATABASE.md](DATABASE.md).

- **`cmd/worker` is thin, wasm-only wiring.** It imports `workers-go`, which exists only for `js/wasm`, so it cannot run in host unit tests. It obtains platform resources and hands them to the composition root; it holds no logic and is excluded from coverage.
- **Logic lives in host-testable `internal/` packages**, tested against fakes.
- **Imports flow downward only.** Packages sit in layers, from shared foundations at the bottom, through parsers of inbound values, data access and the route boundary, up to features and the composition root. A package may import any layer below its own, skipping layers freely, and never one above it or beside it: siblings in a layer, features above all, do not import each other. `depguard` in `.golangci.yml` enforces this and is the source of truth for the layer list, so a new package is placed in a layer there, and a violation fails the lint instead of waiting for review.
- **Inbound values are parsed once, at the bottom, into unforgeable types.** Everything a client sends (path, query, cookie, body field) is turned by a parser into a type with an unexported field, never `type X string`, because a conversion would bypass the parser. Lower layers accept only those types, so they cannot be handed unvalidated input. Parsers **refuse, never rewrite**: they do not trim, case-fold or normalise, so one stored value has exactly one client spelling and two layers cannot disagree about what was stored. A parser's error is a classified client error carrying the type's code. Every bound is a constant beside its type and names the schema constraint it must fit inside; integers stay within what a JavaScript number holds exactly (2^53-1), because D1 moves numbers through JS as `float64`.
- **All SQL lives in one package**, one exported method per atomic operation, all behind a single batch port, with reads as one-statement batches. Atomicity is therefore reviewed in one place, next to the SQL comments that argue for it, and feature code never writes a query. Business outcomes come back as typed values or sentinels the caller maps to a client code; infrastructure failures come back already classified. See [DATABASE.md](DATABASE.md).
- **The route boundary declares credential and access per route.** A feature exports its routes as data: method, path, body limit, whether it needs a credential at all, the access an authenticated caller must have (a scope, plus whether it is session-only or refuses agents, or `auth.Open()` for a valid credential and nothing more), and the handler. One boundary does everything that precedes a handler, in a fixed order (method, media type, body limit, authentication, access, path ids), and the handler runs only after every check passes. The media type is declared per route: JSON by default, or form-urlencoded for an endpoint a standard fixes, which is allowed only on a route that takes no credential because that type is no cross-site defence. The error format is declared per route too: the API's own, or a standard's, and it covers every failure of the route, the boundary's included. The declaration is the whole access rule, so reviewing permissions means reading a table. Leaving the credential or the access unset is a construction-time panic, never a public route. An admin scope also requires the administrator role: the role is the primary gate and scopes only narrow it ([permissions_design.md](permissions_design.md)).
- **The composition root is the only place that wires, and it validates completeness.** Every dependency of every feature is required; a missing one panics at start, so there is no degraded mode, no "nil store, answer 503" fallback and no behaviour that exists only when something was wired.
- **Handlers are pure** (`Request` to `Result[Response]`). One boundary, `internal/httpapi`, does everything that touches HTTP, and `internal/apierr` classifies failures so no cause or internal detail reaches a client. Their package docs are the contract. The same `Result` chain is the default for error flow below the handlers; see [CONTRIBUTING.md](CONTRIBUTING.md#error-flow-result-first) for when to unwrap it and when to fall back to `if err != nil`.
- **TinyGo's `net/http` differs from Go's** (for example, `ServeMux` never matches method-qualified patterns). Host tests cannot catch this, which is a large part of why e2e tests exist.
- **Why not test or lint under `js/wasm`.** The toolchain can compile and vet for it but cannot practically run tests there, and `workerd` would not be the runner. So logic stays out of wasm-only files, only `cmd/worker` is vetted and linted for `js/wasm`, and the real TinyGo build is exercised by e2e.
