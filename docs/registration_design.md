# Registration: design rationale

> This document explains *why* registration is shaped the way it is. It is not a spec: the code is authoritative for what exists. Byte layouts below illustrate an idea. Do not add details of features to this document, only describe overall intent if it changes.

Related: [invitations_design.md](invitations_design.md), [first_run_design.md](first_run_design.md), [login_design.md](login_design.md), [secrets_design.md](secrets_design.md)

## The problem

authsu accounts are usernameless and passwordless: an account *is* a passkey. Registration turns an [invitation](invitations_design.md) into an account plus its first passkey.

The invitation design gives registration one non-negotiable requirement: **there is exactly one moment where the invitation is checked and the account is created, and nothing before that moment leaves anything behind.** No pending users, no reserved ids, no spent-but-unused invitation uses. That is what rules out shadow identities and invitations drained by abandoned attempts.

The tension is that WebAuthn registration takes two round trips, and that cannot be avoided:

1. The server issues a challenge *before* the browser calls `navigator.credentials.create()`. A challenge generated by the client would defeat replay protection.
2. The browser sends the resulting attestation back *afterwards*.

So there is a two-step protocol and a requirement that step one has no side effects. The rest of this document reconciles the two.

## Step one is stateless; step two is the point of acceptance

- **`begin` writes nothing.** It produces what the browser needs for the passkey ceremony. It may *read*, to check the invitation and fail fast before the user goes through a biometric prompt for a code that would be refused anyway, but that check is advisory.
- **`finish` decides everything.** It is the only place that checks whether the invitation is usable, enforces its limits and the first-run rule, and creates the account. Those are conditions *of* the write, not checks before it.

The cost of a stateless `begin` is that whatever must stay consistent between the two calls has to travel through the client, which cannot be trusted. Working out what must be carried, and protecting it, is the core of the design.

## Which identifiers exist

- **The user id** is the server's permanent identifier for an account.
- **The user handle** is the WebAuthn `user.id`. The server chooses it, the passkey stores it during the ceremony, and it comes back on every later login.
- **The credential id** identifies one passkey. The authenticator chooses it, and the server first learns it at `finish`.
- **The challenge** is the server's freshness token for one ceremony.

The difficulty is the user handle: it has to be fixed at `begin`, because the authenticator stores it, but `begin` may not create anything.

The resolution is that **the user handle does not have to be the user id.** A login finds the account by credential id, and the handle is then only a consistency check, so the server needs a mapping from passkey to account, made at `finish`. That decouples the two:

- The **user handle** is random, created at `begin`, and means nothing on its own, as the spec recommends: it lives on the user's devices and should not carry identifying data.
- The **user id** is created at `finish`, inside the write that creates the account. No id exists before the account does, so there is nothing to reserve, leak or clean up.

## Carrying state through the client: a signed challenge

`finish` has to trust three things that `begin` decided:

1. **The challenge is ours and fresh**, the basic guarantee against replay.
2. **Which user handle was issued.** A registration response does not echo it back.
3. **Which invitation the ceremony was started for.** Otherwise any challenge could be paired with any code at `finish`.

A stored challenge would carry all three, but it is exactly the side effect `begin` must avoid: anyone could call `begin` repeatedly and fill a table. Instead, the challenge itself carries the state, signed by the server.

### The return path

The browser builds the *client data*, a small JSON document describing the request, and sends it back. The browser writes it, not the page: the `challenge` field is our challenge copied byte for byte, and the `origin` field is filled in by the browser, which is what makes passkeys resistant to phishing.

At registration nothing we can check signs it. With attestation `none` no signature over it reaches us, so the client data, the flags, the credential id and the transports are all the registering client's claims. What makes registration trustworthy is the invitation, our signed challenge, and TLS. Login is different: the assertion signs the client data and the authenticator data, so login takes user verification from what it signs, never from what registration stored.

The challenge is the only field we control, so anything `begin` wants back at `finish` has to fit inside it.

### One blob, one signature

```
state     = version || expires_at || nonce              -- the nonce is the user handle
signature = HMAC(K, state || H(invitation_code) || H(name))
challenge = state || signature
```

The invitation code is **an input to the signature but not part of the blob.** Its hash is mixed into the HMAC and never transmitted. The account name is bound the same way, because `begin` returns it in the creation options and a client could otherwise begin with one name and finish with another. This is the "associated data" idea from authenticated encryption: the signature commits to it, and the verifier supplies it independently. At `finish` the client sends the code and the name again, and the server recomputes the signature from the state it got back and the hashes of what it just received. A mismatch means the challenge was forged, altered, or created for a different code or name.

Only after the signature verifies does the server read the expiry, so a client-chosen expiry is never acted on. It also refuses an expiry further ahead than the ceremony timeout, which is what limits a leaked key. Hashing the code and name to a fixed width first means two different pairs can never produce the same bytes.

Consequences of this shape:

- **The code never appears in the challenge**, which travels through browser internals, extensions and debugging tools.
- **The blob is signed, not encrypted.** Nothing in it is secret: the browser already sees the user handle.
- **The version** lets the layout change without ambiguity for challenges still in flight.
- **A fixed binary layout, not a general-purpose token format or JSON.** It keeps the challenge small and avoids parsing a general-purpose token format in a security-critical place.
- **The challenge is read only from the client data**, the one copy the authenticator's response is bound to. A separate field would let a client show one challenge to our check and another to the authenticator.

The nonce is the only random part, 32 bytes, so every `begin` produces a unique challenge, which is what the spec's entropy requirement exists to provide. A deterministic handle would silently break this, so it is tested.

The spec sets a minimum challenge size and no maximum. Authenticators only ever see a hash of the client data, so size matters only to browsers and password managers, and the challenge stays within a small multiple of what they handle routinely. The server bounds every client-supplied input it parses, so a request that could only be an attempt to make it read more is refused before parsing.

### Where this departs from the spec

The spec says a relying party *should* store the challenge until the operation completes, so that verification does not depend on the client. We deliberately do not. The signature gives the same guarantee without storage: a client can neither produce a challenge we did not issue nor alter one we did. Single use comes from the account instead (next section). This is a conscious trade to keep `begin` free of side effects.

### Single use, without storage

A stateless challenge cannot be marked used, and it does not need to be: each challenge carries exactly one user handle, user handles are unique across accounts, so a challenge can produce at most one account. Resubmitting the same attestation also collides on the credential id. A challenge never used to finish stays valid until it expires, and its short expiry bounds that window.

### What the signing key is and is not

- **A leaked key cannot create accounts.** It protects the integrity of the ceremony and authorizes nothing: an attacker who can forge challenges still needs a redeemable invitation at `finish`.
- **Rotating it is cheap.** Only ceremonies in flight break.
- **It is never used where a signature is authorization.** The deployed secret is root key material, and each ceremony derives its own key from it with a distinct context. Credentials need no signing key at all, because they are [secrets](secrets_design.md), so this root secret never stands between an attacker and an account.

It is its own secret rather than being derived from `FIRST_RUN_SECRET`, because registration keeps working long after bootstrap is over ([first_run_design.md](first_run_design.md)).

## Deployment configuration

Registration, login and the routes that need a credential share three settings:

| Name | Kind | Purpose |
|---|---|---|
| `AUTH_HMAC_SECRET` | secret | Root key material for ceremony challenges. Each purpose derives its own key from it with a distinct context, so no caller holds the root secret. |
| `API_ORIGIN` | var | Where this Worker is served. It is the identity of the service, wherever the service has to name itself. |
| `UI_ORIGIN` | var | Where the UI is served. Ceremonies run on the UI's pages, so it is the one origin ceremonies are accepted from, and the one origin allowed to call the API cross-origin ([login_design.md](login_design.md#the-ui-on-another-origin)). |

Both origins must be bare origins, `https` except for `localhost`. The relying party is derived from `UI_ORIGIN`, never configured separately, so it cannot disagree with it. Its ID is the UI's host, and it is **permanent**: every passkey is bound to it, so changing the UI's host invalidates every registered passkey. A deployment cannot choose a parent domain as the ID.

The relying party and the origin come from configuration, never from the request, because a `Host` header is attacker-influenced and a Worker is reachable on several hostnames. While configuration is missing or invalid, every route that needs it refuses with a configuration error, and the reason goes only to the log.

## The point of acceptance

At `finish`, once the challenge and the passkey are verified, the account is created in one indivisible operation, and **the authorization checks are conditions of the insert itself**: the invitation resolves (it is active and unexpired), it has room for another account, and if it is the first-run invitation, no account exists at all. A separate "check, then insert" would race, because there are no interactive transactions: two people finishing at once on a single-use code, or two browsers racing to become the first admin, could both pass. Folding the checks into the write lets the database admit exactly one.

The account and its first passkey are created together, because an account with no credential can never be signed into. Both writes go in one batch, which runs as a transaction. A conditional insert that matches nothing is not an error, so the passkey references the account: when the invitation check fails, the passkey's write fails with it and the whole batch rolls back.

The new account's role is copied from the invitation in the same write. The client has no say in it, and this is how the first-run invitation produces the first admin with no admin-specific logic in registration.

## Verification

What `finish` accepts is deliberately narrow, and everything outside it fails closed:

- **Attestation `none` only.** There is no signature or certificate chain to parse, and chain parsing is where most WebAuthn parser bugs live. Accepting other formats later is a deliberate change.
- **One algorithm, ES256.** The key must be a well-formed point on the curve with nothing we do not understand, and we store our own canonical encoding of it.
- **One spelling for everything.** CBOR, base64url and the client data are each accepted only in their single canonical form. Anything a lenient decoder would quietly accept (duplicates, case variants, padding, trailing bytes) is refused, so a document cannot mean one thing to the browser and another to us.
- **Authenticator data** must match our relying party, have user presence and user verification, carry the new credential, and contain nothing we did not ask for.
- **Transports are a hint.** They are stored as reported rather than verified, and an oversized list is the only thing refused.
- **The account name and the invitation code are parsed once, and refused rather than corrected.** The name is strict printable text, because it is what an administrator recognises an account by. The code is an invitation token in its exact shape ([secrets_design.md](secrets_design.md)).

The signature counter is not stored: synced passkeys always report zero. The parsers are fuzzed, with the property that anything accepted is a bounded credential id and a key that round-trips byte for byte.

## Decisions

- **`begin` writes nothing; `finish` is the single point of acceptance**, with every authorization check inside its write.
- **The user handle is random and decoupled from the user id**, which exists only once the account does.
- **State travels in a signed challenge**, with the invitation code and the name bound in as associated data.
- **A code that is not well formed and a code that is not redeemable are different statuses**, but why a code is not redeemable (unknown, used up, revoked, expired) is never revealed.
- **The role comes from the invitation**, never the client.
- **`finish` issues no session.** Registering a passkey is the whole job; signing in is [login](login_design.md).

## Open questions

- Whether `begin` needs rate limiting. That depends on whether low-entropy invitation codes are ever allowed.
- Which further attestation formats, if any, to accept.
