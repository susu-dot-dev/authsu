# Registration: design rationale

> This document explains *why* registration is shaped the way it is. It is not a spec. Request shapes, byte layouts, and SQL fragments below illustrate an idea; the code is authoritative for what actually exists.

Related: [invitations_design.md](invitations_design.md), [first_run_design.md](first_run_design.md)

## The problem

authsu accounts are usernameless and passwordless: an account *is* a passkey. Registration has to turn an [invitation code](invitations_design.md) into an account plus its first passkey.

The invitation design gives registration one non-negotiable requirement: **there is exactly one moment where the invitation is checked and the account is created, and nothing before that moment leaves anything behind.** No pending users, no reserved ids, no spent-but-unused invitation uses. That is what rules out shadow identities and invitations drained by abandoned attempts.

The tension is that WebAuthn registration takes two round trips, and that can't be avoided:

1. The server has to issue a challenge *before* the browser calls `navigator.credentials.create()`. A challenge generated by the client would defeat replay protection.
2. The browser sends the resulting attestation back *afterwards*.

So we have a two-step protocol and a requirement that step one has no side effects. The rest of this document reconciles the two.

## Step one is stateless; step two is the point of acceptance

The shape that follows directly from the requirement is:

- **`begin` writes nothing.** It produces what the browser needs to run the passkey ceremony and returns it. It may *read*, to check the invitation code and fail fast before the user goes through a biometric prompt for a code that would be rejected anyway, but that check is advisory. `begin` is also where rate limiting would go if it is ever needed.
- **`finish` decides everything.** It is the only place that checks whether the invitation is usable, enforces caps and the first-run rule, and creates the account. These are not checks that merely run before a write. They are conditions *of* the write (see below).

The cost of a stateless `begin` is that whatever must stay consistent between the two calls has to travel through the client, and the client can't be trusted. Working out exactly what must be carried, and protecting it, is the core of the design.

## Which identifiers exist, and which one is actually the problem

Several "ids" are involved, and conflating them causes most of the confusion here:

- **The internal user id** is the server's permanent identifier for an account.
- **The user handle** is the WebAuthn `user.id`. It is chosen by the server, written into the passkey during the ceremony, and returned on every later login.
- **The credential id** identifies one specific passkey. It is chosen by the *authenticator*, not by us, and the server first learns it at `finish`.
- **The challenge** is the server's freshness token for one ceremony.

The difficulty is the user handle. It has to be fixed at `begin`, because the authenticator stores it during the ceremony, but `begin` is not allowed to create anything.

The resolution: **the user handle does not have to be the internal user id.** A future login locates the account by credential id, and the user handle is then just a consistency check. So the server only needs a stored mapping, made at `finish`, from passkey to account. That decouples the two:

- The **user handle** is random, created at `begin`, and means nothing on its own. The WebAuthn spec recommends this anyway: the handle lives on the user's devices and should not carry meaningful or identifying data.
- The **internal user id** is created at `finish`, inside the same write that creates the account. No id exists before the account does, so there is nothing to reserve, leak, or clean up.

## Carrying state through the client: a signed challenge

`finish` has to be able to trust three things that `begin` decided:

1. **The challenge is ours and fresh.** This is the basic WebAuthn guarantee against replay.
2. **Which user handle was issued.** A registration response, unlike a login, does *not* echo the handle back. Without help, `finish` would have no trustworthy way to know what handle the new passkey contains.
3. **Which invitation the ceremony was started for.** Without this, any challenge could be paired with any code at `finish`, which disconnects the ceremony from the invitation that authorized it.

A stored challenge row would carry all three easily, but it is exactly the kind of side effect `begin` must avoid. Anyone could call `begin` repeatedly and fill a table that then needs expiry and cleanup. Instead, the challenge itself carries the state, signed by the server.

### The return path: what `clientDataJSON` is

To understand where the state travels, it helps to know what the browser sends back. During the ceremony the browser builds a small JSON document, the *client data*, describing the request. It is roughly:

```json
{"type":"webauthn.create","challenge":"<the challenge, base64url>","origin":"https://auth.example.com","crossOrigin":false}
```

Several properties of this document matter here:

- **The browser writes it, not us and not the page script.** The `challenge` field is our challenge, copied byte for byte and base64url-encoded. The `origin` field is filled in by the browser, which is what makes passkeys resistant to phishing.
- **It is effectively signed by the passkey.** The authenticator never sees the JSON itself. It receives only the SHA-256 hash of it and signs over that hash. So once real attestation verification exists, the challenge inside `clientDataJSON` is covered by the passkey's own signature as well as ours.
- **Other fields may appear.** The spec allows extra and reordered fields (such as `topOrigin` for cross-origin iframes), so we parse it as JSON and don't match it as a fixed string.

The challenge is the only field we control, so any state that `begin` wants back at `finish` has to fit inside it.

### One blob, one signature

The challenge is a single opaque byte string made of two parts concatenated together:

```
challenge = state || tag

state = version || expires_at || user_handle        -- illustrative layout
tag   = HMAC(K, state || SHA-256(invitation_code))
```

So it really is "`{blob, sig}`", flattened into bytes. There is no second payload and no separate token. The browser hands the whole thing back unchanged, inside `clientDataJSON`.

The invitation code is the subtle part. It is **an input to the signature, but it is not part of the blob.** Its hash is mixed into the HMAC computation and is never transmitted. This is the same idea as "associated data" in authenticated encryption: the signature commits to it, and the verifier has to supply it independently in order to verify. At `finish`, the client sends the code again in the request body. The server recomputes the tag from the `state` it got back plus the hash of the code it just received, and compares the result in constant time. A mismatch means one of four things:

- the challenge was forged;
- the challenge was altered;
- the challenge was minted for a different code;
- the request is just malformed.

If the tag matches, the server checks that `expires_at` hasn't passed, and then trusts `user_handle`.

Some consequences of this shape:

- **The code never appears in the challenge.** The challenge travels through browser internals, password-manager extensions, and debugging tools. The code is a secret, so only its influence on the tag travels with the challenge.
- **The blob is signed but not encrypted.** That is fine because nothing in it is secret: the browser already sees the user handle in the creation options. Integrity is all we need.
- **The version byte** lets us change the layout later (for example, to bind more data) without ambiguity about how to parse old challenges still in flight.
- **The expiry is inside the signed state**, so a client can't extend it. The spec suggests challenges stay valid for about the upper end of the ceremony timeout range, which is 5 to 10 minutes. Our expiry should match the timeout we send in the creation options.
- **A fixed binary layout, not a JWT or JSON.** A compact layout keeps the challenge small (see the size budget below) and avoids parsing a general-purpose token format in a security-critical place.

### Size budget

The spec sets a **minimum** for challenges (at least 16 bytes of entropy) but **no maximum**. The obvious worry would be authenticators, especially security keys with small message limits. They turn out not to matter, because the authenticator only ever receives the 32-byte hash of `clientDataJSON`, however large the challenge is. Hybrid (phone-as-authenticator) transport works the same way. The challenge's size can only matter to the *client* side: browsers, OS passkey APIs, and password-manager extensions, which handle the JSON options and the client data directly.

We could not find documented upper limits for those clients, and we shouldn't rely on one existing. Instead we stay within a small multiple of what the ecosystem handles routinely; the spec's own examples use 32-byte challenges. The illustrative layout above is about 73 bytes:

| Part | Size |
|------|------|
| version | 1 byte |
| expiry | 8 bytes |
| user handle | 32 bytes |
| tag | 32 bytes |

That encodes to roughly 100 base64url characters, which makes `clientDataJSON` about 200 bytes in total. The one hard limit nearby is the spec's 64-byte cap on `user.id`, and the 32-byte handle is well inside it.

If size ever matters, there are easy levers:

- a 16-byte user handle is still unguessable;
- the HMAC tag can be truncated to 16 bytes;
- the expiry can be stored in fewer bytes.

Together those shrink the challenge to around 40 bytes. Whatever the final layout, the passkey PR should confirm it works on the major browsers, both mobile platforms, and at least one password-manager extension. The server should also put its own cap on the `clientDataJSON` size it is willing to parse, since it is client-supplied input.

### Where this departs from the spec's advice

The WebAuthn spec says a relying party *SHOULD store the challenge temporarily* until the operation completes. The purpose is that verification shouldn't depend on the client behaving honestly. We deliberately don't store it. The signature achieves the same purpose without storage: a client can't produce a challenge we didn't issue, and it can't alter one we did. The other thing storage would provide, single use, comes from uniqueness constraints on the account instead (next section). This is a conscious trade made to keep `begin` free of side effects, and future readers should not mistake it for an oversight.

### Single use, without storage

A stateless challenge can't be marked "used". It doesn't need to be, because the account it produces enforces uniqueness:

- Each challenge carries exactly one user handle.
- User handles are unique across accounts.
- So a challenge can produce at most one account. Replaying it, even with a new passkey, collides with the account it already made.
- Resubmitting the same attestation also collides on the credential id.

What remains is that a challenge never used to finish stays valid until it expires. The short expiry (minutes) bounds that window, and the signature still requires a valid invitation to accomplish anything.

### What the signing key is and isn't

It is worth being precise about what a leaked signing key would allow, because that determines how carefully the key must be handled:

- **A leaked key cannot create accounts by itself.** The signature protects the integrity of the ceremony. It does not authorize anything. An attacker with the key can forge challenges but still needs a redeemable invitation at `finish`. The invitation remains the only authorization, as the invitation design intends.
- **Rotating the key is cheap.** Rotation breaks only ceremonies in flight, which is a few minutes' worth of retries. That is acceptable.
- **The key must not be reused for anything where a signature *is* authorization,** such as sessions. If a session token were signed with the same key, a leak would mean account takeover. So the deployed secret is treated as root key material, and each purpose derives its own key from it with a distinct context. This is a constraint on future work as much as a description of current work.

The key needs its own secret rather than being derived from `FIRST_RUN_SECRET`, because registration has to keep working long after the bootstrap secret is retired ([first_run_design.md](first_run_design.md)).

## The point of acceptance

At `finish`, after the challenge and passkey are verified, account creation happens as one indivisible database operation. Its essential property is that **the authorization checks are conditions of the insert itself**, not reads that happen before it. Roughly:

```sql
-- illustrative
INSERT INTO users (...)
SELECT ... FROM invitations
WHERE <code matches> AND <not revoked> AND <not expired>
  AND <accounts from this invitation < cap>
  AND <not first-run, or no users exist at all>;
-- and, in the same transaction, the credential row for that user
```

This matters because there are no interactive transactions available to us. A separate "check, then insert" would race: two people finishing at once on a single-use code, or two browsers racing to become the first admin, could both pass the check. Folding the checks into the write lets the database serialize them and admit exactly one.

The account and its first passkey must be created together. An account with no credential can never be signed into, and is exactly the kind of partial state this design exists to prevent. Both writes go in one D1 batch, which D1 runs as a transaction and rolls back as a whole if any statement fails. One subtlety: a conditional insert that matches no rows is not an error, so on its own it wouldn't trigger the rollback. Making the credential reference the account (enforced by foreign key, which D1 enforces by default) turns "the invitation check failed" into a failure of the batch, so no credential can be written without its account.

The role of the new account is copied from the invitation as part of the same write. The client has no say in it, and this is how the first-run invitation produces the first admin with no admin-specific logic in registration.

## Open questions

- How to verify attestations under TinyGo's constraints, and which attestation formats to accept.
- How the relying-party ID and origin are configured.
- What session is issued after `finish`, and its key derivation (see the key-separation constraint above).
- Whether `begin` needs rate limiting. This is driven by whether low-entropy invitation codes are ever allowed.
